1//! The `Box<T>` type for heap allocation.
2//!
3//! [`Box<T>`], casually referred to as a 'box', provides the simplest form of
4//! heap allocation in Rust. Boxes provide ownership for this allocation, and
5//! drop their contents when they go out of scope. Boxes also ensure that they
6//! never allocate more than `isize::MAX` bytes.
7//!
8//! # Examples
9//!
10//! Move a value from the stack to the heap by creating a [`Box`]:
11//!
12//! ```
13//! let val: u8 = 5;
14//! let boxed: Box<u8> = Box::new(val);
15//! ```
16//!
17//! Move a value from a [`Box`] back to the stack by [dereferencing]:
18//!
19//! ```
20//! let boxed: Box<u8> = Box::new(5);
21//! let val: u8 = *boxed;
22//! ```
23//!
24//! Creating a recursive data structure:
25//!
26//! ```
27//! # #[allow(dead_code)]
28//! #[derive(Debug)]
29//! enum List<T> {
30//!     Cons(T, Box<List<T>>),
31//!     Nil,
32//! }
33//!
34//! let list: List<i32> = List::Cons(1, Box::new(List::Cons(2, Box::new(List::Nil))));
35//! println!("{list:?}");
36//! ```
37//!
38//! This will print `Cons(1, Cons(2, Nil))`.
39//!
40//! Recursive structures must be boxed, because if the definition of `Cons`
41//! looked like this:
42//!
43//! ```compile_fail,E0072
44//! # enum List<T> {
45//! Cons(T, List<T>),
46//! # }
47//! ```
48//!
49//! It wouldn't work. This is because the size of a `List` depends on how many
50//! elements are in the list, and so we don't know how much memory to allocate
51//! for a `Cons`. By introducing a [`Box<T>`], which has a defined size, we know how
52//! big `Cons` needs to be.
53//!
54//! # Memory layout
55//!
56//! For non-zero-sized values, a [`Box<T, A>`] will use its allocator of type `A` for its allocation.
57//! It is valid to convert both ways between a `Box` and a raw pointer allocated with `A`, so long as:
58//! - the size of the pointee, as reported by [`size_of_val`], is non-zero,
59//! - the [`Layout::for_value`] of the pointee [*fits*](Allocator#memory-fitting) the memory block, and
60//! - the pointee is a valid instance of `T` (for the given metadata of the pointer).
61//!
62//! For zero-sized values, a [`Box<T, A>`] may use any sufficiently aligned non-null pointer.
63//! While it is sound to convert a zero-sized allocation from `A` into a `Box`, as
64//! long as it is backed by a valid value of `T`, doing so may lead to memory leaks, as
65//! the destructor of [`Box`] will not call [`deallocate`](Allocator::deallocate)
66//! on zero-sized values. It is recommended to use [`ptr::dangling`] instead.
67//!
68//! Likewise, manually deallocating the raw pointer acquired from a `Box` is only sound
69//! if the size of the pointee is non-zero, as zero-sized values may be represented by
70//! a pointer that is not [*currently allocated*] by that allocator. It is recommended to
71//! pair [`Box::into_raw_with_allocator`] with [`Box::from_raw_in`], rather than
72//! doing this.
73//!
74//! Note that even the [`Global`] allocator might not use dangling pointers for
75//! zero-sized allocations, even though *most* implementations do this.
76//!
77//! So long as `T: Sized`, a `Box<T>` is guaranteed to be represented
78//! as a single pointer and is also ABI-compatible with C pointers
79//! (i.e. the C type `T*`). This means that if you have extern "C"
80//! Rust functions that will be called from C, you can define those
81//! Rust functions using `Box<T>` types, and use `T*` as corresponding
82//! type on the C side. As an example, consider this C header which
83//! declares functions that create and destroy some kind of `Foo`
84//! value:
85//!
86//! ```c
87//! /* C header */
88//!
89//! /* Returns ownership to the caller */
90//! struct Foo* foo_new(void);
91//!
92//! /* Takes ownership from the caller; no-op when invoked with null */
93//! void foo_delete(struct Foo*);
94//! ```
95//!
96//! These two functions might be implemented in Rust as follows. Here, the
97//! `struct Foo*` type from C is translated to `Box<Foo>`, which captures
98//! the ownership constraints. Note also that the nullable argument to
99//! `foo_delete` is represented in Rust as `Option<Box<Foo>>`, since `Box<Foo>`
100//! cannot be null.
101//!
102//! ```
103//! #[repr(C)]
104//! pub struct Foo;
105//!
106//! #[unsafe(no_mangle)]
107//! pub extern "C" fn foo_new() -> Box<Foo> {
108//!     Box::new(Foo)
109//! }
110//!
111//! #[unsafe(no_mangle)]
112//! pub extern "C" fn foo_delete(_: Option<Box<Foo>>) {}
113//! ```
114//!
115//! Even though `Box<T>` has the same representation and C ABI as a C pointer,
116//! this does not mean that you can convert an arbitrary `T*` into a `Box<T>`
117//! and expect things to work. `Box<T>` values will always be fully aligned,
118//! non-null pointers. Moreover, the destructor for `Box<T>` will attempt to
119//! free the value with the global allocator. In general, the best practice
120//! is to only use `Box<T>` for pointers that originated from the global
121//! allocator.
122//!
123//! **Important.** At least at present, you should avoid using
124//! `Box<T>` types for functions that are defined in C but invoked
125//! from Rust. In those cases, you should directly mirror the C types
126//! as closely as possible. Using types like `Box<T>` where the C
127//! definition is just using `T*` can lead to undefined behavior, as
128//! described in [rust-lang/unsafe-code-guidelines#198][ucg#198].
129//!
130//! # Considerations for unsafe code
131//!
132//! **Warning: This section is not normative and is subject to change, possibly
133//! being relaxed in the future! It is a simplified summary of the rules
134//! currently implemented in the compiler.**
135//!
136//! The aliasing rules for `Box<T>` are the same as for `&mut T`. `Box<T>`
137//! asserts uniqueness over its content. Using raw pointers derived from a box
138//! after that box has been mutated through, moved or borrowed as `&mut T`
139//! is not allowed. For more guidance on working with box from unsafe code, see
140//! [rust-lang/unsafe-code-guidelines#326][ucg#326].
141//!
142//! # Editions
143//!
144//! A special case exists for the implementation of `IntoIterator` for arrays on the Rust 2021
145//! edition, as documented [here][array]. Unfortunately, it was later found that a similar
146//! workaround should be added for boxed slices, and this was applied in the 2024 edition.
147//!
148//! Specifically, `IntoIterator` is implemented for `Box<[T]>` on all editions, but specific calls
149//! to `into_iter()` for boxed slices will defer to the slice implementation on editions before
150//! 2024:
151//!
152//! ```rust,edition2021
153//! // Rust 2015, 2018, and 2021:
154//!
155//! # #![allow(boxed_slice_into_iter)] // override our `deny(warnings)`
156//! let boxed_slice: Box<[i32]> = vec![0; 3].into_boxed_slice();
157//!
158//! // This creates a slice iterator, producing references to each value.
159//! for item in boxed_slice.into_iter().enumerate() {
160//!     let (i, x): (usize, &i32) = item;
161//!     println!("boxed_slice[{i}] = {x}");
162//! }
163//!
164//! // The `boxed_slice_into_iter` lint suggests this change for future compatibility:
165//! for item in boxed_slice.iter().enumerate() {
166//!     let (i, x): (usize, &i32) = item;
167//!     println!("boxed_slice[{i}] = {x}");
168//! }
169//!
170//! // You can explicitly iterate a boxed slice by value using `IntoIterator::into_iter`
171//! for item in IntoIterator::into_iter(boxed_slice).enumerate() {
172//!     let (i, x): (usize, i32) = item;
173//!     println!("boxed_slice[{i}] = {x}");
174//! }
175//! ```
176//!
177//! Similar to the array implementation, this may be modified in the future to remove this override,
178//! and it's best to avoid relying on this edition-dependent behavior if you wish to preserve
179//! compatibility with future versions of the compiler.
180//!
181//! [*currently allocated*]: Allocator#currently-allocated-memory
182//! [ucg#198]: https://github.com/rust-lang/unsafe-code-guidelines/issues/198
183//! [ucg#326]: https://github.com/rust-lang/unsafe-code-guidelines/issues/326
184//! [dereferencing]: core::ops::Deref

233/// An internal wrapper for the pointer + `PhantomData` inside a `Box`.
234/// This type has no semantic meaning. It only exists because the layout of
235/// `Box` is hard-coded into the compiler, and because moving the
236/// auto trait impls to `Box` would cause regressions (#162850).
237#[repr(transparent)]
238struct BoxRaw<T: ?Sized> {
239    pointer: NonNull<T>,
240    _marker: PhantomData<T>,
241}
242
243unsafe impl<T: ?Sized + Send> Send for BoxRaw<T> {}
244unsafe impl<T: ?Sized + Sync> Sync for BoxRaw<T> {}
245impl<T: ?Sized + core::panic::UnwindSafe> core::panic::UnwindSafe for BoxRaw<T> {}
246impl<T: ?Sized, U: ?Sized> CoerceUnsized<BoxRaw<U>> for BoxRaw<T> where T: Unsize<U> {}
247impl<T: ?Sized, U: ?Sized> DispatchFromDyn<BoxRaw<U>> for BoxRaw<T> where T: Unsize<U> {}

251    /// `ptr` must be non-null

254        // SAFETY: Upheld by the caller
255        unsafe { BoxRaw { pointer: NonNull::new_unchecked(ptr), _marker: PhantomData } }
256    }
257
258    #[inline]
259    const fn cast<U>(self) -> BoxRaw<U> {
260        BoxRaw { pointer: self.pointer.cast(), _marker: PhantomData }
261    }
262

265        self.pointer
266    }
267

269    const fn as_ptr(self) -> *mut T {
270        self.pointer.as_ptr()
271    }
272
273    #[inline]
274    #[cfg(not(no_global_oom_handling))]
275    const fn dangling() -> Self
276    where
277        T: Sized,
278    {
279        BoxRaw { pointer: NonNull::dangling(), _marker: PhantomData }
280    }
281}

313/// Monomorphic function for allocating an uninit `Box`.
314#[inline]
315// The is a separate function to avoid doing it in every generic version, but it
316// looks small to the mir inliner (particularly in panic=abort) so leave it to
317// the backend to decide whether pulling it in everywhere is worth doing.
318#[rustc_no_mir_inline]
319#[cfg_attr(miri, track_caller)] // even without panics, this helps for Miri backtraces
320#[cfg(not(no_global_oom_handling))]
321#[rustc_const_unstable(feature = "const_heap", issue = "79597")]
322const fn box_new_uninit(layout: Layout) -> *mut u8 {
323    if layout.size() == 0 {
324        return layout.dangling_ptr().as_ptr();
325    }
326    match Global.allocate(layout) {
327        Ok(ptr) => ptr.as_mut_ptr(),
328        Err(_) => handle_alloc_error(layout),
329    }
330}

350    /// Allocates memory on the heap and then places `x` into it.
351    ///
352    /// This doesn't actually allocate if `T` is zero-sized.
353    /// See the [memory layout] section for more details.
354    ///
355    /// # Examples
356    ///
357    /// ```
358    /// let five = Box::new(5);
359    /// ```
360    ///
361    /// [memory layout]: self#memory-layout
362    #[cfg(not(no_global_oom_handling))]
363    #[inline(always)]
364    #[stable(feature = "rust1", since = "1.0.0")]
365    #[must_use]
366    #[rustc_diagnostic_item = "box_new"]
367    #[cfg_attr(miri, track_caller)] // even without panics, this helps for Miri backtraces
368    pub fn new(x: T) -> Self {
369        // This is `Box::new_uninit` but inlined to avoid build time regressions.
370        let ptr = box_new_uninit(<T as SizedTypeProperties>::LAYOUT) as *mut T;
371        // Nothing below can panic so we do not have to worry about deallocating `ptr`.
372        // SAFETY: we just allocated the box to store `x`.
373        unsafe { core::intrinsics::write_via_move(ptr, x) };
374        // SAFETY: we just initialized the memory `ptr` points to.
375        unsafe { mem::transmute(ptr) }
376    }

568    ///
569    /// # Examples
570    ///
571    /// ```
572    /// #![feature(allocator_ext)]
573    ///
574    /// use std::alloc::System;
575    ///

577    /// // Deferred initialization:
578    /// five.write(5);
579    /// let five = unsafe { five.assume_init() };
580    ///
581    /// assert_eq!(*five, 5)
582    /// ```
583    #[unstable(feature = "allocator_ext", issue = "163177", implied_by = "allocator_api")]
584    #[cfg(not(no_global_oom_handling))]
585    #[must_use]

779    ///
780    /// `f` is called on the value in the box, and the result is returned, also boxed.
781    ///
782    /// Note: this is an associated function, which means that you have
783    /// to call it as `Box::map(b, f)` instead of `b.map(f)`. This
784    /// is so that there is no conflict with a method on the inner type.
785    ///
786    /// # Examples
787    ///
788    /// ```
789    /// let b = Box::new(7);
790    /// let new = Box::map(b, |i| i + 7);

795    pub fn map<U>(this: Self, f: impl FnOnce(T) -> U) -> Box<U, A> {
796        let (value, allocation) = Box::take(this);
797        let (raw, alloc) = Box::into_non_null_with_allocator(allocation);
798        if size_of::<T>() == size_of::<U>() && align_of::<T>() == align_of::<U>() {
799            // SAFETY: We checked that the memory requirements are the same for both types
800            // and `raw` is already a valid pointer for the requisite memory.
801            let allocation = unsafe { Box::from_non_null_in(raw.cast::<MaybeUninit<U>>(), alloc) };
802            Box::write(allocation, f(value))
803        } else {
804            if size_of::<T>() != 0 {
805                // SAFETY: `raw` isn't dangling since it points to a non-zero-sized
806                // allocation and is never used again after this point.
807                unsafe { alloc.deallocate(raw.cast(), Layout::for_value(&value)) }
808            }
809            Box::new_in(f(value), alloc)
810        }
811    }

936    /// Allocates memory in the given allocator then clones `src` into it, returning an error if allocation fails.
937    ///
938    /// This doesn't actually allocate if `src` is zero-sized.
939    /// See the [memory layout] section for more details.
940    ///
941    /// # Examples
942    ///
943    /// ```
944    /// #![feature(clone_from_ref)]
945    ///
946    /// use std::alloc::System;
947    ///
948    /// let hello: Box<str, System> = Box::try_clone_from_ref_in("hello", System)?;
949    /// # Ok::<(), std::alloc::AllocError>(())
950    /// ```
951    ///
952    /// [memory layout]: self#memory-layout
953    #[unstable(feature = "clone_from_ref", issue = "149075")]
954    //#[unstable(feature = "allocator_ext", issue = "163177", implied_by = "allocator_api")]
955    #[inline]
956    pub fn try_clone_from_ref_in(src: &T, alloc: A) -> Result<Box<T, A>, AllocError> {
957        struct DeallocDropGuard<'a, A: Allocator>(Layout, &'a A, NonNull<u8>);
958        impl<'a, A: Allocator> Drop for DeallocDropGuard<'a, A> {
959            fn drop(&mut self) {
960                let &mut DeallocDropGuard(layout, alloc, ptr) = self;
961                // SAFETY: `ptr` was allocated by `*alloc` with layout `layout`
962                unsafe {
963                    alloc.deallocate(ptr, layout);
964                }
965            }
966        }
967        let layout = Layout::for_value::<T>(src);
968        let (ptr, guard) = if layout.size() == 0 {
969            (layout.dangling_ptr(), None)
970        } else {
971            // Safety: layout is non-zero-sized
972            let ptr = alloc.allocate(layout)?.cast();
973            (ptr, Some(DeallocDropGuard(layout, &alloc, ptr)))
974        };
975        let ptr = ptr.as_ptr();
976        // SAFETY: `*ptr` is newly allocated (or a ZST), correctly aligned to
977        // `align_of_val(src)`, and is valid for writes for `size_of_val(src)`.
978        // If this panics, then `guard` will deallocate for us (if allocation occuured)
979        unsafe {
980            <T as CloneToUninit>::clone_to_uninit(src, ptr);
981        }
982        // Defuse the deallocate guard
983        core::mem::forget(guard);
984        // SAFETY: We just initialized `*ptr` as a clone of `src`
985        Ok(unsafe { Box::from_raw_in(ptr.with_metadata_of(src), alloc) })
986    }
987}

1703    /// Constructs a box from a `NonNull` pointer in the given allocator.
1704    ///
1705    /// After calling this function, the `NonNull` pointer is owned by
1706    /// the resulting `Box`. Specifically, the `Box` destructor will call
1707    /// the destructor of `T` and free the allocated memory, except
1708    /// in the cases described in the [memory layout] section.
1709    ///
1710    /// # Safety
1711    ///
1712    /// This function is unsafe because improper use may lead to
1713    /// memory problems. For example, a double-free may occur if the
1714    /// function is called twice on the same raw pointer.
1715    ///
1716    /// The exact safety requirements are described in the [memory layout] section, together
1717    /// with recommendations about how to handle the special case of zero-sized allocations
1718    /// correctly.
1719    ///
1720    /// In particular, if the size of the pointee, as reported by [`size_of_val`], is
1721    /// nonzero, then the raw pointer must point to a block of memory allocated by
1722    /// `alloc`.
1723    /// If the size of the pointee is zero, then the raw pointer can be any
1724    /// sufficiently aligned pointer, e.g. [`NonNull::dangling`].
1725    ///
1726    /// Note that the [considerations for unsafe code] apply to all `Box<T, A>` values.
1727    ///
1728    /// # Examples
1729    ///
1730    /// Recreate a `Box` which was previously converted to a `NonNull` pointer
1731    /// using [`Box::into_non_null_with_allocator`]:

1734    ///

1736    /// let (non_null, alloc) = Box::into_non_null_with_allocator(x);
1737    /// let x = unsafe { Box::from_non_null_in(non_null, alloc) };
1738    /// ```
1739    /// Manually create a `Box` from scratch by using the system allocator:
1740    /// ```
1741    /// use std::alloc::{Allocator, Layout, System};
1742    ///
1743    /// unsafe {
1744    ///     let non_null = System.allocate(Layout::new::<i32>())?.cast::<i32>();
1745    ///     // In general .write is required to avoid attempting to destruct
1746    ///     // the (uninitialized) previous contents of `non_null`.
1747    ///     non_null.write(5);
1748    ///     let x = Box::from_non_null_in(non_null, System);

1750    /// # Ok::<(), std::alloc::AllocError>(())
1751    /// ```

1762    /// Consumes the `Box`, returning a wrapped raw pointer and the allocator.
1763    ///
1764    /// The pointer will be properly aligned and non-null.
1765    ///
1766    /// After calling this function, the caller is responsible for the
1767    /// memory previously managed by the `Box`. In particular, the
1768    /// caller should properly destroy `T` and release the memory, taking
1769    /// into account the [memory layout] used by `Box`. The easiest way to
1770    /// do this is to convert the raw pointer back into a `Box` with the
1771    /// [`Box::from_raw_in`] function, allowing the `Box` destructor to perform
1772    /// the cleanup.
1773    ///
1774    /// While manually deallocating the pointer through [`deallocate`]
1775    /// is possible, you must only do this if the pointee's size, as reported by
1776    /// [`size_of_val`], is non-zero (the `Box` may be a dangling pointer
1777    /// otherwise). See the [memory layout] section for more details.
1778    ///
1779    /// Note: this is an associated function, which means that you have
1780    /// to call it as `Box::into_raw_with_allocator(b)` instead of `b.into_raw_with_allocator()`. This
1781    /// is so that there is no conflict with a method on the inner type.
1782    ///
1783    /// # Examples
1784    /// Converting the raw pointer back into a `Box` with [`Box::from_raw_in`]
1785    /// for automatic cleanup:
1786    /// ```
1787    /// use std::alloc::System;
1788    ///
1789    /// let x = Box::new_in(String::from("Hello"), System);
1790    /// let (ptr, alloc) = Box::into_raw_with_allocator(x);
1791    /// let x = unsafe { Box::from_raw_in(ptr, alloc) };
1792    /// ```
1793    /// Manual cleanup by explicitly running the destructor and deallocating
1794    /// the memory:
1795    /// ```
1796    /// use std::alloc::{Allocator, Layout, System};
1797    /// use std::ptr::{self, NonNull};
1798    ///
1799    /// let x = Box::new_in(String::from("Hello"), System);
1800    /// let (ptr, alloc) = Box::into_raw_with_allocator(x);
1801    /// unsafe {
1802    ///     ptr::drop_in_place(ptr);
1803    ///     let non_null = NonNull::new_unchecked(ptr);
1804    ///     alloc.deallocate(non_null.cast(), Layout::new::<String>());
1805    /// }
1806    /// ```
1807    ///
1808    /// [memory layout]: self#memory-layout
1809    /// [`deallocate`]: Allocator::deallocate
1810    #[must_use = "losing the pointer will leak memory"]
1811    #[stable(feature = "allocator_api", since = "1.100.0")]
1812    #[rustc_const_unstable(feature = "const_heap", issue = "79597")]
1813    #[inline]
1814    pub const fn into_raw_with_allocator(b: Self) -> (*mut T, A) {
1815        let mut b = mem::ManuallyDrop::new(b);
1816        // We carefully get the raw pointer out in a way that Miri's aliasing model understands what
1817        // is happening: using the primitive "deref" of `Box`. In case `A` is *not* `Global`, we
1818        // want *no* aliasing requirements here!
1819        // In case `A` *is* `Global`, this does not quite have the right behavior; `into_raw`
1820        // works around that.
1821        let ptr = &raw mut **b;
1822        // SAFETY: See above.
1823        let alloc = unsafe { ptr::read(&b.1) };
1824        (ptr, alloc)
1825    }

2216// equivalence when cloning boxes.
2217impl<T: Clone, A: Allocator + Clone> Clone for Box<T, A> {
2218    /// Returns a new box with a `clone()` of this box's contents.
2219    ///
2220    /// # Examples
2221    ///
2222    /// ```
2223    /// let x = Box::new(5);
2224    /// let y = x.clone();
2225    ///
2226    /// // The value is the same
2227    /// assert_eq!(x, y);
2228    ///
2229    /// // But they are unique objects
2230    /// assert_ne!(&*x as *const i32, &*y as *const i32);
2231    /// ```
2232    #[inline]
2233    fn clone(&self) -> Self {
2234        // Pre-allocate memory to allow writing the cloned value directly.
2235        let mut boxed = Self::new_uninit_in(self.1.clone());
2236        // SAFETY: Destination pointer is valid and will then become initialised.
2237        unsafe {
2238            (**self).clone_to_uninit(boxed.as_mut_ptr().cast());
2239            boxed.assume_init()
2240        }
2241    }
2242
2243    /// Copies `source`'s contents into `self` without creating a new allocation.
2244    ///
2245    /// # Examples
2246    ///
2247    /// ```
2248    /// let x = Box::new(5);
2249    /// let mut y = Box::new(10);
2250    /// let yp: *const i32 = &*y;
2251    ///
2252    /// y.clone_from(&x);
2253    ///
2254    /// // The value is the same
2255    /// assert_eq!(x, y);
2256    ///
2257    /// // And no allocation occurred
2258    /// assert_eq!(yp, &*y);
2259    /// ```
2260    #[inline]
2261    fn clone_from(&mut self, source: &Self) {
2262        (**self).clone_from(&(**source));
2263    }
2264}

2274    /// Copies `source`'s contents into `self` without creating a new allocation,
2275    /// so long as the two are of the same length.
2276    ///
2277    /// # Examples
2278    ///
2279    /// ```
2280    /// let x = Box::new([5, 6, 7]);
2281    /// let mut y = Box::new([8, 9, 10]);
2282    /// let yp: *const [i32] = &*y;

2290    /// assert_eq!(yp, &*y);
2291    /// ```
2292    fn clone_from(&mut self, source: &Self) {
2293        if self.len() == source.len() {
2294            self.clone_from_slice(source);
2295        } else {
2296            *self = source.clone();
2297        }

2516// A pointer can only be pin safe if it does not implement certain safe traits
2517// maliciously. Since `Box` is fundamental, downstream crates may be able to
2518// implement those traits for `Box<LocalType>`, so we must carefully check that
2519// this is not a problem for each trait.
2520//
2521// The `Box` type always implements `Deref` and `DerefMut`, so despite being
2522// fundamental, downstream crates cannot implement these traits for
2523// `Box<LocalType>`.
2524//
2525// Conversely, downstream crates are able to implement `Clone`, `Debug`, and
2526// `Display` for `Box<LocalType>` as long as `LocalType` does not implement
2527// said trait. However, the `Box<T>` type does not treat the existence of an
2528// `&Box<T>` as evidence that the `T` is not pinned, so this is not
2529// problematic.
2530//
2531// Finally, even if downstream crates provide their own implementation of
2532// `Clone` for `Box<LocalType>`, it is not problematic for the cloned box to be
2533// wrapped in `Pin`, since the same conversion could have been carried out
2534// safely as `Box::pin((*p).clone())`.
