1#[doc(attribute = "must_use")]
2//
3/// Warn when a value is ignored.
4///
5/// The `must_use` attribute applies to values where simply creating or returning them is
6/// often not enough. If a value marked with `#[must_use]` is produced and then ignored, the
7/// compiler warns through the [`unused_must_use`] lint.
8///
9/// This is most common on types that represent an important state or outcome. For example,
10/// [`Result`] is marked `#[must_use]` because ignoring an error value can hide a failed operation.
11/// In the following example, the returned [`Result`] is the only sign that writing the message
12/// might have failed:
13///
14/// ```
15/// # #![allow(unused_must_use)]
16/// fn write_message() -> std::io::Result<()> {
17///     // Write the message...
18///     Ok(())
19/// }
20///
21/// write_message();
22/// ```
23///
24/// Ignoring that [`Result`] triggers this warning:
25///
26/// ```text
27/// warning: unused `Result` that must be used
28///   = note: this `Result` may be an `Err` variant, which should be handled
29///   = note: `#[warn(unused_must_use)]` (part of `#[warn(unused)]`) on by default
30/// help: use `let _ = ...` to ignore the resulting value
31/// ```
32///
33/// Future values are also `#[must_use]`: creating a future does not run it, so ignoring one often
34/// means the intended asynchronous work never happens.
35///
36/// You can also place `#[must_use]` on a function, method, or trait declaration. On a function or
37/// method, the warning is tied to ignoring that call's return value:
38///
39/// ```
40/// # #![allow(unused_must_use)]
41/// #[must_use]
42/// fn make_token() -> String {
43///     String::from("token")
44/// }
45///
46/// // Ignoring this call's return value triggers `unused_must_use`.
47/// make_token();
48/// ```
49///
50/// On a trait, the warning applies when a function returns an opaque type (`impl Trait`) or trait
51/// object (`dyn Trait`) whose bounds include that trait. This is how futures warn if you create one
52/// but never poll or await it, since an `async fn` returns an opaque type implementing [`Future`].
53///
54/// The attribute can include a message explaining what the caller should do with the value:
55///
56/// ```
57/// # #![allow(dead_code)]
58/// #[must_use = "call `.finish()` to complete the operation"]
59/// fn start_operation() -> Operation {
60///     Operation
61/// }
62///
63/// struct Operation;
64/// ```
65///
66/// If intentionally ignoring the value is correct, bind it to `_` or call [`drop`]:
67///
68/// ```
69/// # #[must_use]
70/// # fn make_token() -> String {
71/// #     String::from("token")
72/// # }
73/// let _ = make_token();
74/// drop(make_token());
75/// ```
76///
77/// The attribute is a warning tool, not a type-system rule. Code can still explicitly discard a
78/// `#[must_use]` value, and the compiler does not require callers to inspect or otherwise act on
79/// the value.
80///
81/// For more information, see the Reference on [the `must_use` attribute].
82///
83/// [`unused_must_use`]: ../rustc/lints/listing/warn-by-default.html#unused-must-use
84/// [the `must_use` attribute]: ../reference/attributes/diagnostics.html#the-must_use-attribute
85const _: () = ();

87#[doc(attribute = "allow")]
88//
89/// The `allow` attribute suppresses lint diagnostics that would otherwise produce
90/// warnings or errors. It can be used on any lint or lint group (except those
91/// set to [`forbid`]).
92///
93/// ```
94/// #[allow(dead_code)]
95/// fn unused_function() {
96///     // ...
97/// }
98///
99/// fn main() {
100///   // `unused_function` does not generate a compiler warning.
101/// }
102/// ```
103///
104/// Without `#[allow(dead_code)]`, the example above would emit:
105///
106/// ```text
107/// warning: function `unused_function` is never used
108///  --> main.rs:1:4
109///   |
110/// 1 | fn unused_function() {
111///   |    ^^^^^^^^^^^^^^^
112///   |
113///   = note: `#[warn(dead_code)]` (part of `#[warn(unused)]`) on by default
114///
115///   warning: 1 warning emitted
116/// ```
117///
118/// Multiple lints can be set to `allow` at once with commas:
119///
120/// ```
121/// #[allow(unused_variables, unused_mut)]
122/// fn main() {
123///     let mut x: u32 = 42;
124/// }
125/// ```
126///
127/// This is mostly used to prevent lint warnings or errors while still under development.
128///
129/// It cannot override a lint that has been set to [`forbid`].
130///
131/// It's also important to consider that overusing `allow` could make code harder to maintain
132/// and possibly hide issues. To mitigate this issue, using the `expect` attribute is preferred.
133///
134/// `allow` can be overridden by [`warn`], [`deny`], and [`forbid`].
135///
136/// The lint checks supported by rustc can be found via `rustc -W help`,
137/// along with their default settings and are documented in [the `rustc` book].
138///
139/// [the `rustc` book]: ../rustc/lints/listing/index.html
140///
141/// For more information, see the Reference on [the `allow` attribute].
142///
143/// [the `allow` attribute]: ../reference/attributes/diagnostics.html#lint-check-attributes
144/// [`forbid`]: ./attribute.forbid.html
145/// [`warn`]: ./attribute.warn.html
146/// [`deny`]: ./attribute.deny.html
147const _: () = ();

149#[doc(attribute = "cfg")]
150//
151/// Used for conditional compilation.
152///
153/// The `cfg` attribute allows compiling an item under specific conditions, otherwise it
154/// will be ignored.
155///
156/// ```
157/// // Only compiles this function for Linux.
158/// #[cfg(target_os = "linux")]
159/// fn platform_specific() {
160///     println!("Running on Linux");
161/// }
162///
163/// // Only compiles this function if not for Linux.
164/// #[cfg(not(target_os = "linux"))]
165/// fn platform_specific() {
166///     println!("Running on something else");
167/// }
168/// ```
169///
170/// Depending on the platform you're targeting, only one of these two functions will be considered
171/// during the compilation.
172///
173/// Conditions can also be combined with `all(...)`, `any(...)`, and `not(...)`:
174///
175/// * `all`: True if all given predicates are true.
176/// * `any`: True if at least one of the given predicates is true.
177/// * `not`: True if the predicate is false and false if the predicate is true.
178///
179/// ```
180/// #[cfg(all(unix, target_pointer_width = "64"))]
181/// fn unix_64bit() {
182///     // ...
183/// }
184/// ```
185///
186/// If you want to use this mechanism in an [`if`] condition in your code, you
187/// can use the [`cfg!`] macro. To conditionally apply an attribute,
188/// see [`cfg_attr`].
189///
190/// For more information, see the Reference on [the `cfg` attribute].
191///
192/// [`cfg_attr`]: ./attribute.cfg_attr.html
193/// [the `cfg` attribute]: ../reference/conditional-compilation.html#the-cfg-attribute
194/// [`if`]: ./keyword.if.html
195const _: () = ();

353#[doc(attribute = "no_std")]
354//
355/// Prevents automatically linking the standard library.
356///
357/// Written as an inner attribute at the top of the crate root, the `no_std` attribute stops
358/// the compiler from linking [`std`] into the crate, and only links [`core`].
359///
360/// The attribute also swaps which prelude gets inserted, with the [`core`] prelude replacing
361/// the [`std`] prelude. Items like [`Option`], [`Result`], and the primitive types remain
362/// available from [`core`] without any imports needed:
363///
364/// ```rust,ignore (no_std)
365/// #![no_std]
366///
367/// fn halve(x: u32) -> Option<u32> {
368///     if x % 2 == 0 { Some(x / 2) } else { None }
369/// }
370/// ```
371///
372/// Anything that requires heap memory allocations is not part of [`core`]. Linking the [`alloc`]
373/// crate explicitly can be used to include these types:
374///
375/// ```rust,ignore (no_std + needs a global allocator to link)
376/// #![no_std]
377///
378/// extern crate alloc;
379///
380/// use alloc::vec::Vec;
381/// ```
382///
383/// A `no_std` binary also removes the startup routine and default panic handler `std`
384/// normally provides. It must define its own `#[panic_handler]`, and typically its own
385/// entry point by additionally using `#![no_main]`:
386///
387/// ```rust,ignore (no_std + needs more than no_main alone to link)
388/// #![no_std]
389/// #![no_main]
390///
391/// use core::panic::PanicInfo;
392///
393/// #[panic_handler]
394/// fn on_panic(_info: &PanicInfo) -> ! {
395///     loop {}
396/// }
397/// ```
398///
399/// For more information, see the Reference on [the `no_std` attribute].
400///
401/// [`std`]: ../std/index.html
402/// [`core`]: ../core/index.html
403/// [`alloc`]: ../alloc/index.html
404/// [`Option`]: option::Option
405/// [`Result`]: result::Result
406/// [the `no_std` attribute]: ../reference/names/preludes.html#the-no_std-attribute
407const _: () = ();

409#[doc(attribute = "no_main")]
410/// Prevents emitting the `main` entrypoint symbol.
411///
412/// Written as an inner attribute at the top of the crate root, the `no_main` attribute prevents
413/// the compiler from generating the program's standard Rust entrypoint, leaving that up to you.
414/// This is useful when some other object being linked into the program defines the entrypoint,
415/// or when you want to define the platform's `main` symbol yourself.
416///
417/// If you define an entry point symbol that is suitable for your target, it must also be exported
418/// under an unmangled name using the [`no_mangle` attribute]:
419///
420/// ```no_run
421/// #![no_main]
422///
423/// use std::ffi::{c_char, c_int};
424///
425/// #[unsafe(no_mangle)]
426/// pub extern "C" fn main(_argc: c_int, _argv: *const *const c_char) -> c_int {
427///     println!("Hello world!");
428///     0
429/// }
430/// ```
431///
432/// Unlike `no_std`, the `no_main` attribute does not prevent the compiler from generating
433/// the startup routine or linking the standard library provided by the operating system's executable [ABI].
434///
435/// [ABI]: https://en.wikipedia.org/wiki/Application_binary_interface
436/// [`no_mangle` attribute]: ../reference/abi.html#the-no_mangle-attribute

439#[doc(attribute = "repr")]
440/// Specifies the [representation] of a type.
441///
442/// Written as an outer attribute on a `struct`, `enum` or `union`, `repr` controls how the
443/// type is laid out in memory. This is needed when passing types across an [FFI] boundary
444/// or whenever you rely on a specific layout.
445///
446/// The available representations are:
447///
448/// * [`Rust`] (the default): the layout is unspecified and may change between compilations.
449/// * [`C`]: the layout follows the rules of the C language for the target platform.
450/// * The [primitive representations] (`u8`, `i32`, `usize`, ...): set the discriminant
451///   type of an enum.
452/// * [`transparent`]: the type has the same layout and ABI as its only non-zero-sized field.
453///
454/// The `align(N)` and `packed(N)` modifiers raise or lower the alignment of a type, respectively.
455/// `N` must be a power of two no greater than 2<sup>29</sup>. The two modifiers cannot be
456/// applied to the same type, and references to fields of a `packed` type cannot be created,
457/// since they may be unaligned.
458///
459/// # Examples
460///
461/// ```
462/// #[repr(C, align(16))]
463/// struct Foo {
464///     first: u32,
465///     second: u32,
466///     third: u32,
467/// }
468///
469/// assert_eq!(align_of::<Foo>(), 16);
470/// // 12 bytes of fields, rounded up to a multiple of the alignment.
471/// assert_eq!(size_of::<Foo>(), 16);
472/// ```
473///
474/// ```
475/// #[repr(C, packed(2))]
476/// struct Foo {
477///     first: u32,
478///     second: u32,
479///     third: u32,
480/// }
481///
482/// assert_eq!(align_of::<Foo>(), 2);
483/// assert_eq!(size_of::<Foo>(), 12);
484/// ```
485///
486/// ```
487/// #[repr(C)]
488/// struct Foo<T> {
489///     item: T,
490/// }
491/// ```
492///
493/// `Foo` is laid out according to the C rules and is guaranteed to be 16-byte aligned.
494///
495/// The representation is a property of the type definition, so it does
496/// parameters: below, `Foo<u8>` and `Foo<u64>` both use the `C` representation. Their actual
497/// layouts still differ, because they depend on `T`.
498///
499/// [representation]: ../reference/type-layout.html#representations
500/// [`Rust`]: ../reference/type-layout.html#the-rust-representation
501/// [`C`]: ../reference/type-layout.html#the-c-representation
502/// [primitive representations]: ../reference/type-layout.html#primitive-representations
503/// [`transparent`]: ../reference/type-layout.html#the-transparent-representation
504/// [FFI]: https://en.wikipedia.org/wiki/Foreign_function_interface
505const _: () = ();

507#[doc(attribute = "inline")]
508//
509/// Suggest that the compiler inline a function at its call sites.
510///
511/// Inlining replaces a call with a copy of the called function's body, which can remove the
512/// overhead of the call. The `inline` attribute is only a hint: the compiler may ignore it, and
513/// it already inlines functions on its own when that looks worthwhile. Poor choices about what to
514/// inline can make a program larger or slower.
515///
516/// Where it does matter is inlining across crate boundaries. A non-generic function is not
517/// normally inlined into another crate, since the calling crate compiles against only its
518/// signature. Marking it `#[inline]` makes the body available to other crates so they can inline
519/// it too:
520///
521/// ```rust
522/// # #![allow(dead_code)]
523/// #[inline]
524/// pub fn square(x: i32) -> i32 {
525///     x * x
526/// }
527/// ```
528///
529/// Generic functions do not need this. They are instantiated in each crate that uses them, so
530/// their bodies are already available to inline.
531///
532/// The attribute applies to functions and has three forms:
533///
534/// - `#[inline]` suggests inlining the function.
535/// - `#[inline(always)]` suggests inlining it at every call site.
536/// - `#[inline(never)]` suggests never inlining it.
537///
538/// You should almost never need `#[inline(always)]`: prefer to let the compiler decide unless
539/// profiling shows a small, hot function that benefits from it. `#[inline(never)]` is useful to
540/// keep a rarely used path, such as a function that only reports an error, out of its caller.
541///
542/// For more information, see the Reference on [the `inline` attribute].
543///
544/// [the `inline` attribute]: ../reference/attributes/codegen.html#the-inline-attribute
545const _: () = ();

549/// Hint to the compiler that a function is unlikely to be called.
550///
551/// Marking a function `#[cold]` tells the compiler that calls to it are rare, so it can

561///         report_error("value must be non-negative");
562///     }
563///     // ... the common case continues here ...
564/// }
565///
566/// #[cold]
567/// fn report_error(message: &str) {
568///     eprintln!("error: {message}");
569/// }
570/// ```
571///
572/// For more information, see the Reference on [the `cold` attribute].
573///
574/// [the `cold` attribute]: ../reference/attributes/codegen.html#the-cold-attribute

577#[doc(attribute = "track_caller")]
578//
579/// Make a function report the location of its caller instead of its own.
580///
581/// When a function panics, the panic message normally points at the line inside that function
582/// where the panic happened. `#[track_caller]` changes that: it lets the function see the
583/// [`Location`] it was called from, so the panic (and any direct use of [`Location::caller`])
584/// points at the call site instead. The standard library uses this on methods like
585/// [`Option::unwrap`], so a failed `unwrap` blames the line that called it rather than a line
586/// inside the standard library.
587///
588/// ```rust,should_panic
589/// #[track_caller]
590/// fn assert_even(n: i32) {
591///     assert!(n % 2 == 0, "{n} is not even");
592/// }
593///
594/// // The panic blames this line, not the `assert!` inside `assert_even`.
595/// assert_even(3);
596/// ```
597///
598/// The attribute applies to functions with the default `"Rust"` ABI, other than `fn main`.
599///
600/// For more information, see the Reference on [the `track_caller` attribute].
601///
602/// [`Location`]: panic::Location
603/// [`Location::caller`]: panic::Location::caller
604/// [`Option::unwrap`]: Option::unwrap
605/// [the `track_caller` attribute]: ../reference/attributes/codegen.html#the-track_caller-attribute
606const _: () = ();

608#[doc(attribute = "proc_macro")]
609//
610/// Defines a function-like procedural macro.
611///
612/// Applied to a `pub` function at the root of a proc-macro crate, `proc_macro` makes that function usable as a macro invoked as
613/// `foo!(...)` in other crates. The function receives the tokens written inside the invocation as a [`TokenStream`] and returns
614/// the [`TokenStream`] that replaces the invocation:
615///
616/// ```rust, ignore (requires depending on the proc-macro crate)
617/// # extern crate proc_macro;
618/// use proc_macro::TokenStream;
619///
620/// #[proc_macro]
621/// pub fn foo(input: TokenStream) -> TokenStream {
622///    "fn answer() -> u32 { 67 }".parse().unwrap()
623/// }
624/// ```
625///
626/// The macro can only be invoked from other crates, not from the crate where it is defined:
627///
628/// ```rust,ignore (requires depending on the proc-macro crate)
629/// use my_macro_crate::foo;
630///
631/// // Expands to `fn answer() -> u32 { 67 }`.
632/// foo!();
633///
634/// fn main() {
635///    println!("{}", answer()); // Prints 67
636/// }
637/// ```
638///
639/// The attribute is only usable with crates of the `proc-macro` crate type, which is set in the crate's `Cargo.toml`
640/// with `proc-macro = true` in the `[lib]` section. Using it anywhere else is a compilation error:
641///
642/// ```text
643///error: the `#[proc_macro]` attribute is only usable with crates of the `proc-macro` crate type
644/// --> src/lib.rs:4:1
645///  |
646/// 4| #[proc_macro]
647///  | ^^^^^^^^^^^^
648/// ```
649///
650/// For more information, see the Reference on [function-like procedural macros] and the [`proc_macro`] crate documentation.
651///
652/// [`TokenStream`]: ../proc_macro/struct.TokenStream.html
653/// [function-like procedural macros]: ../reference/procedural-macros.html#the-proc_macro-attribute
654/// [`proc_macro`]: ../proc_macro/index.html
655const _: () = ();

683#[doc(attribute = "non_exhaustive")]
684//
685/// Indicates that a type might have more fields or variants added in the future.
686///
687/// Placing `#[non_exhaustive]` on a struct or enum tells code in other crates not to assume
688/// the definition is complete. This lets a library add new fields or variants without breaking
689/// existing code.
690///
691/// On an enum, code outside the defining crate must include a wildcard arm when matching:
692///
693/// ```rust,ignore (cross-crate effect only)
694/// // in crate `errors`:
695/// #[non_exhaustive]
696/// pub enum ConnectionError {
697///     Refused,
698///     Timeout,
699/// }
700///
701/// // in another crate:
702/// use errors::ConnectionError;
703///
704/// match error {
705///     ConnectionError::Refused => println!("connection refused"),
706///     ConnectionError::Timeout => println!("timed out"),
707///     _ => println!("other error"), // required because of #[non_exhaustive]
708/// }
709/// ```
710///
711/// On a struct, code outside the defining crate cannot construct instances using struct literal
712/// syntax:
713///
714/// ```rust,ignore (cross-crate effect only)
715/// // in crate `config`:
716/// #[non_exhaustive]
717/// pub struct Config {
718///     pub width: u32,
719///     pub height: u32,
720/// }
721///
722/// // in another crate:
723/// use config::Config;
724///
725/// let c = Config { width: 800, height: 600 }; // ERROR: cannot construct
726/// ```
727///
728/// Inside the defining crate, exhaustive matching and direct construction are still allowed.
729///
730/// For more information, see the Reference on [the `non_exhaustive` attribute].
731///
732/// [the `non_exhaustive` attribute]: ../reference/attributes/type_system.html#the-non_exhaustive-attribute
733const _: () = ();

735#[doc(attribute = "automatically_derived")]
736//
737/// The `automatically_derived` attribute is used to indicate that an `impl` block is automatically
738/// generated by a [derive macro]. It has no direct effect, but it may be used by tools and
739/// diagnostic lints, such as [Clippy], to detect these automatically generated implementations.
740///
741/// Example:
742///
743/// ```rust
744/// // Given #[derive(Clone)] on struct Example, the derive macro may produce:
745/// #[automatically_derived]
746/// impl ::core::clone::Clone for Example {
747///     fn clone(&self) -> Self { Example }
748/// }
749/// # struct Example;
750/// ```
751///
752/// The attribute may only be applied to an `impl` block.
753///
754/// Because code generated by a macro becomes part of the source code representation of the crate
755/// that calls the macro, diagnostic lints for the expanded macro will be emitted in the caller's
756/// workspace (whereas warnings generated while building dependencies not in the local workspace
757/// are suppressed by Cargo). This may be undesirable, so the author of the macro can use the
758/// `automatically_derived` attribute to hint to tools that the generated code is not written by the
759/// caller (and that tools should not render warnings for it).
760///
761/// For example, this `impl` block lacks `#[automatically_derived]`:
762///
763/// ```rust
764/// // Suppose this impl block is the output of a derive macro
765/// impl ::core::cmp::PartialEq for Example {
766///     fn eq(&self, other: &Self) -> bool { true }
767///     fn ne(&self, other: &Self) -> bool { !(self == other) }
768/// }
769/// # struct Example;
770/// ```
771///
772/// In the example above, Clippy will emit the following warning:
773///
774/// ```text
775/// warning: re-implementing `PartialEq::ne` is unnecessary
776///  --> src/lib.rs:7:9
777///   |
778/// 4 |         fn ne(&self, other: &Self) -> bool { !(self == other) }
779///   |         ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
780///   |
781///   = help: for further information visit https://rust-lang.github.io/rust-clippy/rust-1.98.0/index.html#partialeq_ne_impl
782///   = note: `#[warn(clippy::partialeq_ne_impl)]` on by default
783/// ```
784///
785/// However, if the derive macro were written so that it outputs `#[automatically_derived]` on the
786/// `impl` block, as below, then Clippy will not emit the above `partialeq_ne_impl` lint:
787///
788/// ```rust
789/// // Suppose this impl block is the output of a derive macro
790/// #[automatically_derived]
791/// impl ::core::cmp::PartialEq for Example {
792///     fn eq(&self, other: &Self) -> bool { true }
793///     fn ne(&self, other: &Self) -> bool { !(self == other) }
794/// }
795/// # struct Example;
796/// ```
797///
798/// The `automatically_derived` attribute should be preferred over the [`allow`] attribute for
799/// suppressing unintended user-facing diagnostics in automatically generated code.
800///
801/// For more information, see the Reference on [the `automatically_derived` attribute].
802///
803/// [`allow`]: ./attribute.allow.html
804/// [derive macro]: ./attr.derive.html
805/// [Clippy]: https://github.com/rust-lang/rust-clippy
806/// [the `automatically_derived` attribute]: ../reference/attributes/derive.html#the-automatically_derived-attribute
807const _: () = ();

809#[doc(attribute = "cfg_attr")]
810//
811/// The `cfg_attr` attribute is used to conditionally apply one or more attributes to an item.
812///
813/// Example:
814///
815/// ```rust
816/// // The struct derives `Debug` when the `debug_impls` feature is enabled.
817/// #[cfg_attr(feature = "debug_impls", derive(Debug))]
818/// struct X;
819/// ```
820///
821/// You can apply multiple attributes by separating them with commas:
822///
823/// ```rust
824/// #[cfg_attr(feature = "nightly", allow(dead_code), deny(unused_variables))]
825/// // This function only gets the `allow(dead_code)` and `deny(unused_variables)` attributes when
826/// // `feature = "nightly"` is active.
827/// fn nightly_only_function() {
828///     let x = 42;
829/// }
830/// ```
831///
832/// For complex conditions, you can combine `all(...)`, `any(...)`, and `not(...)`.
833///
834/// * `all`: True if all given predicates are true.
835/// * `any`: True if at least one of the given predicates is true.
836/// * `not`: True if the predicate is false.
837///
838/// ```rust
839/// #[cfg_attr(
840///     all(feature = "system", feature = "disk"),
841///     doc = "These docs only show up if both `system`, and `disk` are enabled.",
842/// )]
843/// mod my_module {
844///     // ...
845/// }
846/// ```
847///
848/// For more information, see the Reference on [the `cfg_attr` attribute].
849///
850/// [`cfg`]: ./attribute.cfg.html
851/// [the `cfg_attr` attribute]: ../reference/conditional-compilation.html#the-cfg_attr-attribute
